# 事实边界与写作方法

## 五类事实

1. **仓库可验证**：代码、README、commit、测试、日志、当前任务包里能直接看到的内容。
2. **用户亲述**：Miki 口头或文字说过的经历、感受、判断。可以写，但要归因为"Miki 说/Miki 认为"，不能包装成仓库证据。
3. **第三方反馈**：用户之外的人给出的评论、反应。必须归因，不能包装成普遍效果；一条反馈不等于普遍结论。
4. **作者推断**：由已知事实推出的判断，写作时要标出"这是推断"，不能写成确定事实。
5. **时效数据**：会随时间变化的数字（下载量、播放量、耗时）。写清基线、范围、统计方法和时间点，局部指标不能外推成整体效果。

材料不足时，最多追问 1-3 个会改变文章主线的问题；用户要求先继续时，保留"待补项"标记，不编造不存在的细节去填空。

## 定策略

写正文前先想清楚：目标读者是谁、这篇要传播的一句话承诺是什么、主矛盾或核心问题是什么、技术主线是什么、Miki 在这篇里的认知/决策变化是什么、结尾自然行动是什么。技术长文/项目故事默认写给两类读者：不会写代码的 vibe coding 用户、会写代码但不擅长表达的技术创作者，除非 Miki 另有说明。再定标题和提纲。

**正式内容项目里，这一步不是重新决策，是执行**：如果项目文件夹里已经有内容设计产出的受众、核心观点和大纲，这些是写正文阶段的权威来源，直接采用，不重新讨论或推翻；发现内容设计没覆盖到的缺口时，只标出缺口向 Miki 确认，不擅自补一套新的受众/观点/大纲静默替换掉已确认的内容。独立写作请求（没有正式项目、没有上游内容设计）时，才由这一步自己完整决定这些问题。

标题可以直接提问，也可以组合数字、投入、结果、反差或身份；只用正文能兑现的元素，不夸大。

## 结构生成原则

"技术长文""小红书图文""视频脚本"只是高层任务类型，不是固定章节模板。每篇现场识别一条主导推进线：

- 事件变化（发生了什么，怎么解决的）
- 认知变化（Miki 一开始怎么想，后来发现了什么）
- 决策变化（面对选择时怎么取舍）
- 实验变化（试了什么方法，结果和预期是否一致）
- 人物关系变化（不常用，Miki 内容更偏项目和技术，谨慎使用）

其他变化可以辅助，但不能抢主线。结构从本篇的事实、冲突、证据、选择和后果里长出来，不套用上一篇写过的结构。相邻两段如果只能用"然后""此外"连接，说明因果没立住，要重建。

## 六步技术写法

技术性段落尽量覆盖：

```
问题 → 为什么难 → 尝试与取舍 → 具体实现 → 可量化结果 → 适用边界
```

术语第一次出现时用一句人话解释，再回到具体的文件、日志、实验或决策。技术深度来自真实的问题和工程取舍，不是堆术语密度。

## 开场与语气

第一句话让事情或问题发生，三句内出现真实冲突、反差、数字或明确疑问；不从"时代背景""行业趋势"或"本文将介绍"开始。

保持 Miki 聪明、坦率、有判断也允许修正的声音：保留自然口语、自嘲和真实情绪；不自动统一润色成"高级感"文风；短段落为主，长短句交替；表格只在明显更清楚时使用（比较、映射、时间线）。

结尾回扣开场和写这篇的初衷，交代当前能力/结论、适用与不适用范围、尚未验证的部分，以及自然行动。行动号召（关注/点赞/转发）像邀请，不硬喊。
