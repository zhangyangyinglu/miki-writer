# 各格式输出规范

## 小红书图文

- **字数**：正文控制在合理的小红书图文篇幅内（大致 600-1000 字为宜，具体以能在一屏到两屏内读完为准），不写成公众号长文的缩短版，而是重新按小红书的阅读节奏组织。
- **话题标签**：给出 3-6 个建议标签，明确告知"这是建议，不是必须照抄"，由用户自己挑选和调整。
- **高风险表达初筛（必须做，但不等于合规保证）**：交付前对照下方清单过一遍，命中的词提醒用户注意、建议替换方向；这是初筛，不是平台审核的替代品，也不保证一定通过审核——是否真的违规高度依赖上下文，不machine性地见词就替换，判断不了的地方标出来让用户自己决定，不要替用户机械替换。
- 语气避免"家人们""绝绝子"等网络热词（如果用户在 `references/ip-signature.md` 里维护了自己的"避免词"清单，以那份为准；文件不存在时参考 `references/ip-signature.example.md` 里的示例）。

### 小红书高风险表达清单（供初筛参考，非机械替换、非合规保证）

这份清单不是法律或平台规则的权威来源，只是常见高风险表达的初筛参考；具体是否违规以小红书当时的实际规则为准，清单本身没有专人定期核验更新。用户发现新的高风险表达可以随时告诉执行 AI 补充进来，判断不了的表达交给用户自己决定。

| 分类 | 常见违禁表达 | 建议替换方向 |
| --- | --- | --- |
| 绝对化用语 / 广告法极限词 | 最好、最佳、第一、顶级、国家级、世界级、极致、绝无仅有、万能、全网最低价、史上最强、No.1、100%、永久 | 用具体感受或范围代替（"我用下来体验不错"而不是"最好用"） |
| 医疗/功效宣称 | 治愈、根治、特效、抗癌、祛痘、抗衰老、美白、淡斑（数码/AI 工具"疗效"化宣传同样要避免） | 换成"我的体验/使用感受"而不是效果承诺 |
| 减肥/瘦身类夸大承诺 | 月瘦X斤、躺瘦、无需运动、三天见效、不反弹（一般用不到，涉及生活方式内容时留意） | 如实描述过程和局限 |
| 金融理财类夸大承诺 | 稳赚不赔、保本保息、日赚X元、零风险、翻倍、财务自由（涉及"用 AI 赚钱"类选题时要特别注意） | 只描述真实数据和方法，不做收益承诺 |
| 跨平台导流 | 加微信、加VX、私聊、留联系方式、点击链接、某宝搜索、某音同名、进群、公众号（直接名） | 需要引导到其他平台时用平台允许的方式表达，不写成硬性导流指令 |
| 诱导互动 | "点赞""收藏""关注""评论区扣1"这类命令式措辞（呼吁本身不违规，命令式语气容易被判定诱导） | 用邀请式语气，比如"如果对你有用，欢迎收藏"而不是"记得点赞收藏" |
| 诱导抢购/虚假营销 | 秒杀、限量、错过不再有、恭喜中奖 | 如实描述 |

## 朋友圈 / 社交动态文案

- **场景定位**：私域、熟人可见的分享，不是公开算法平台，不需要话题标签，也不用小红书那种"钩子开头"结构；语气按用户平时发朋友圈的样子写，比小红书图文更随性、更短。
- **篇幅**：一般几十到两百字；配图时文字可以更短，留空间给图。
- **链接与可见范围自查（必须做）**：
  - 文案里如果带项目/仓库链接，确认链接本身是公开可访问的，不是只有用户自己能打开的私有地址。
  - 不在文案里带具体的个人文件路径、内部文件命名（比如 Obsidian 里的文件夹结构、内部任务包文件名），这些是操作细节，不是分享内容。
  - 提到协作者、朋友或任何第三方时，需要用户明确同意才能点名；默认不点名，只描述做了什么。
- **克制表达**：不夸大项目的完成度或效果（比如没人用过就不要说"帮到很多人"）；如实说清楚这是自己做着玩/自用工具/正在测试，不需要包装成成熟产品发布。
- **避免词**：同样遵守 `references/ip-signature.md` 里的"避免的表达"清单（文件不存在时参考 `references/ip-signature.example.md`），emoji 克制使用，不刻意堆砌。
- 本 Skill 只出文案和配图建议文本（见"配图建议"一节），不生成、不选择实际图片，也不会替用户实际发布到朋友圈——发布动作需要用户自己操作。

## 公众号长文

- 分小标题分段，每个小标题对应一个明确的信息推进点，不做纯装饰性分节。
- 长短句交替，避免大段无标点的长段落；技术段落覆盖六步写法（见 `facts-and-writing.md`）。

## 技术长文一键多平台分发

写完一篇技术长文/项目故事的主稿后，如果用户要多平台分发，按平台各自的格式规范（本文件对应小节）重新组织，不是简单裁剪：

1. 先确认主稿的事实、结构和结论不变——多平台分发改的是表达方式和篇幅，不是重新编事实。
2. 逐个平台产出：公众号（长文分段）、小红书（控制字数+话题标签建议+高风险表达初筛）。目前只做这两个平台；用户需要别的平台时单独说，不默认扩展。
3. 每个版本产出后，附上"配图建议"（见下一节），不需要用户额外再问一次。
4. 全部版本先标"AI草稿｜待确认"，用户逐个确认或修改，不假设全部照单全收。

## 配图建议（不生成图片，只出文字建议）

本 Skill 不生成、不选择、不下载任何实际图片，只提供三类可选的文字建议，由用户自己执行或转交给能生成/搜图的工具：

- **AI 生图提示词**：给 1-3 条简短的生图提示词（画面主体、风格、避免项），不写复杂的分镜级要求。
- **GitHub 截图清单**：如果文章讲的是一个真实项目，指出"建议截哪张图"（比如某个文件的目录结构、某段关键代码、某次真实的终端输出/测试结果），只指出截图对象和理由，不生成截图本身。
- **Skill/项目信息图思路**：需要一张概括"这个东西是什么"的图时，给出信息图应该包含哪几块内容（比如"能力清单 + 一句话价值 + 状态"），不是具体的视觉设计稿。

配图建议默认只在小红书图文、朋友圈文案、技术长文（含多平台分发）这三类要求里主动给出；其他格式（口播稿/视频脚本、README）已经有自己的画面/封面对应机制，不重复给。

## 口播稿 / 视频脚本 / 提词器稿

有上游项目规划文件（比如你自己维护的内容 Brief、大纲文件）时，先读取确认范围和已经定好的观点，不重新讨论；产出两部分内容：

- **自然口述稿**：正常说话的语序和口气，不分镜；需要提词器版时另起一节给出逐句停顿版本，两者不要混在一起。
- **视频脚本**：台词、画面、素材、节奏和分镜对照，用表格呈现：

  | 分镜 | 台词 | 画面 | 素材 | 节奏/时长 | 备注 |
  | --- | --- | --- | --- | --- | --- |

  最后一行是结尾分镜。如果你有下游负责拍摄清单/剪辑执行的工具或流程，这份表格是它的权威输入，字段命名不要在交接时随意更改。

没有上游项目文件、只是独立请求时，口述稿和视频脚本可以合并成一份输出，仍然保留"台词/画面"的对应关系，不能只给口播稿没有画面提示。

具体交付成什么文件、放在哪里，由你自己的项目结构决定，这份 Skill 不假定固定的文件命名或编号约定。

- **开头/结尾固定话术**：读取 `references/ip-signature.md`（不存在时参考 `references/ip-signature.example.md` 并提醒用户先填一份自己的）里的"已确认"话术；文件都不存在、用户也没当场给说法时，不要自己编一句固定开头/结尾，直接问用户想怎么开场收尾。
- 每个分镜要写清楚画面提示（拍什么/展示什么素材），不是只有口播稿没有画面提示。
- 其余署名呈现方式（图文类如何标注 IP）如果用户还没想清楚，见 `references/ip-signature.md`，标记为待补充，不要自己替用户决定。

## GitHub README

- 默认只交付 `README.md`。是否额外产出其他语言版本（比如英文 `README_EN.md`，顶部提供相对链接互相切换语言）按用户明确要求来，不默认双语。
- 产出其他语言版本时按目标语言读者的写作习惯重写，不逐句机翻。
- 标题和一句话价值之后，优先放 Star 引导、有效徽章、社区信号；专业感来自可运行示例、架构说明、测试和维护状态，不来自夸张营销词。
- 用户要求新增许可证时，优先采用权利范围匹配的成熟现成协议原文，不自行拼接条款。

### 公开分享的 Skill 包 README（2026-09-08 确认）

- **能力是主角，作者不是**：标题、开场价值主张、能力清单，主语都是"这个 skill 能做什么"，不是"作者是谁/作者多厉害"。作者身份只在边界说明、署名规则这类必须交代来源的地方出现，不单独写一段介绍作者本人。
- **明确说清依赖的工具，不要含糊成"通用适配"**：这份 skill 依赖哪个具体工具（比如 Obsidian），直接在开头讲清楚，不要用"你也可以换成别的笔记软件，自己摸索"这种回避表述——如果 skill 本来就只针对一个工具设计，就直说，不要为了显得开放而模糊必需条件。
- **给不懂 AI 的人写一份能跟着做的安装指引**：分享对象里有不熟悉 AI 工具、甚至没装过依赖工具的人时，README 要包含"怎么装依赖工具（如 Obsidian）→ 怎么把这个 skill 接入自己的 AI 工具（Claude/Codex/其他）"这两段可操作步骤，不能假设读者已经知道 skill 是什么、怎么装。界面按钮名称可能随版本变化，写成"大致操作 + 建议以官方最新说明为准"，不把易变的 UI 细节写成不会过时的事实。
