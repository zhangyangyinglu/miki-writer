# 交互式网页（HTML）方法

这是一种交付形式，不是一种新的内容规则——正文遵循的事实边界、文风、去 AI 味标准和其他模式完全一样，变的只是最终呈现从 Markdown/纯文本变成一个可以点、可以切换、可以看图表的网页。

## 什么时候用这个模式

- 技术长文/项目故事想要一个比 Markdown 更好读的网页版（比如带可折叠的技术细节、可以切换的"问题/方案"对比）。
- GitHub README 想嵌入一个可以实际操作的小演示，而不是一张静态截图。
- 需要一个独立的介绍页/落地页，不依附于某一篇具体文章。

不确定要不要用这个模式时，先问 Miki：这次是要一份好读的文字稿，还是真的需要读者动手点/切换/看数据。不是每篇文章都需要网页版。

## 技术约束（必须遵守）

- **单文件自包含**：一个 `.html` 文件搞定，CSS 写在 `<style>` 里，JS 写在 `<script>` 里，不依赖构建工具、不依赖本地起服务器，双击就能在浏览器里打开。
- **默认不引入外部依赖**：优先用原生 HTML/CSS/JS 实现交互（`<details>`/`<summary>` 做展开收起、原生 JS 做 tab 切换、SVG 或 `<canvas>` 做简单图表）。确实需要更复杂的图表库时，可以通过 CDN 的 `<script src>` 引入一个成熟的开源库（比如 Chart.js），但要在交付时明确告诉 Miki："这个版本需要联网加载图表库，离线打开图表可能不显示"，不要不声不响地加依赖。
- **响应式**：桌面和手机屏幕都要能正常看，不假设固定宽度。
- **不写后端逻辑**：不做数据库、不做用户登录、不处理表单提交到服务器——这些是"应用"，不是"一篇带交互的内容"，超出这个模式的范围。如果 Miki 的需求听起来像要做一个真正的应用，提醒她这可能需要另外的工程支持，不是这个 Skill 该做的事。

## 视觉与交互设计

- 不是把 Markdown 正文塞进一个好看的模板——先想清楚这篇内容适合哪种交互形式：技术对比适合 tab 切换，长篇技术细节适合默认收起、点击展开，时间线或数据适合图表化，纯叙事内容可能根本不需要交互，老实做成排版精美的静态页就够。
- 保留原稿的结构生成原则：找一条主导推进线，不为了"看起来有交互感"硬塞导航栏、进度条、锚点这些装饰性交互。
- 配色、字体、留白按内容本身的调性来定，不是每次都套同一个视觉模板；避免过度设计掩盖内容本身。
- 深色/浅色模式不强制，Miki 有要求时再做。

## 内容边界（和其他模式一致，不因为换了呈现形式就放松）

- 正文事实边界、去 AI 味标准、终稿保护规则完全适用，按 `references/facts-and-writing.md`、`references/de-ai-calibration.md` 执行。
- 页面里的图表和数据要能追溯到真实来源，不为了"看起来有交互性"编造演示数据；确实是示意性质的占位数据时，必须在页面上明确标注"示意数据"，不能让读者误以为是真实统计。
- 小说模式的内容如果也要做成网页版，遵循 `references/fiction-writing.md` 的规则，不适用事实边界。

## 交付

产出一个完整的 `.html` 文件，先标 `AI草稿｜待确认`。不自动部署、不自动上传到任何托管服务、不自动生成公开链接——这些动作需要 Miki 在对话中单独明确授权，本 Skill 只交付文件本身。
